### ADR-001: .NET for the whole system — Accepted
**Context.** Logistico needs web, desktop and mobile clients plus a high-performance backend, built by one team. The project chose .NET (and, at first, the look of DevExpress VCL).
**Decision.** C# on .NET 10 LTS for backend, web UI, device services and future native apps.
**Alternatives.** TypeScript front end + .NET back end; Java/Kotlin; Go.
**Consequences.** One language and toolchain; contracts and rules shared between browser and server; Blazor components can be reused in MAUI Hybrid apps later. Hiring targets .NET developers.

### ADR-002: Web first with Blazor WebAssembly + REST API — Accepted
**Context.** Users should open Logistico in the browser. Iraqi connectivity is unstable. Mobile apps and partners need an API anyway.
**Decision.** Blazor Web App with global WebAssembly interactivity. The UI runs in the browser and calls `/api/v1` on the same origin.
**Alternatives.** Interactive Server (round-trip per click, sensitive to dropped connections); Auto mode (complexity of dual-mode components).
**Consequences.** Larger first download (cached afterwards); stateless servers that scale horizontally; the same API serves future clients.

### ADR-003: DevExpress Blazor — Superseded by ADR-016
**Context.** VCL look and feel is a core requirement.
**Decision.** DevExpress Blazor 26.1 (Fluent theme, Small size). Grid in server mode through `GridDevExtremeDataSource` + `DevExtreme.AspNet.Data`.
**Alternatives.** Telerik (DockManager, no Ribbon found), Syncfusion (Ribbon; heavier load; community licence limits), Radzen/MudBlazor (free; far from VCL).
**Consequences.** Per-developer subscription and licence key. No docking manager: use splitters/tabs, build later if needed.
**Superseded (18 Oct 2026).** A commercial licence was not an option. DevExpress was removed from the code; see ADR-016.

### ADR-004: PostgreSQL — Accepted
**Decision.** PostgreSQL (16 in local development, 18 in CI/production), EF Core 10 + Npgsql, schema per module, snake_case, UUIDv7 keys generated in .NET.
**Consequences.** Free and portable; PostGIS/TimescaleDB available later; no SQL Server licences.

### ADR-005: Custom modular monolith + ASP.NET Core Identity — Accepted
**Decision.** One ASP.NET Core host loads modules (Shipments first). ASP.NET Core Identity provides users, roles, cookies, 2FA and passkeys.
**Alternatives.** Microservices (premature); Keycloak (extra server); DevExpress XAF (fast CRUD, less UX control).
**Consequences.** Simple deployment. Boundaries kept by architecture tests (ADR-006). SSO can be added through Identity external logins or an OIDC server later.

### ADR-006: Two projects per module — Accepted
**Decision.** `Logistico.Modules.X` (internal: domain, persistence, endpoints; one public `XModule` entry point) and `Logistico.Modules.X.Contracts` (DTOs, validation attributes, pure rules) shared with the browser.
**Consequences.** Validation and rules run identically in browser and server. Architecture tests fail the build on boundary violations.

### ADR-007: No prerendering; auth state from the API — Accepted
**Context.** With prerendering, client components also run on the server (double data loading, server needs client services).
**Decision.** `InteractiveWebAssemblyRenderMode(prerender: false)`. The client asks `/api/v1/account/me`. Account pages stay server-rendered with their own layout.
**Consequences.** Simpler, predictable components; a short "Signing in…" state on first load.

### ADR-008: Optimistic concurrency with xmin + ETag — Accepted
**Decision.** PostgreSQL `xmin` as the row version; `GET` returns an ETag; state changes need `If-Match` (428 if missing, 412 if stale).
**Consequences.** No lost updates when two clerks edit the same shipment; offline clients get explicit conflicts.

### ADR-009: Desktop app approach — Proposed
**Recommendation.** Start with the **installable web app (PWA) + LX Device Service**. Move to **.NET MAUI Blazor Hybrid** (same components) if offline or multi-window needs grow. Build a native **Avalonia UI** console only if power users need true docking and native performance (DevExpress WPF is out while there is no licence). Options compared in [09](09-client-applications.md) §4.

### ADR-010: LX Device Service — Proposed
**Recommendation.** A .NET 10 Native AOT service on workstations and site edge nodes for printers (ZPL/TSPL/ESC-POS, OS spooler), scales and serial scanners, reachable from the browser over `wss://localhost` with API-signed requests. Details in [06](06-device-integration.md).

### ADR-011: Event bus — Proposed
**Recommendation.** Transactional outbox in PostgreSQL + **NATS JetStream** (Apache 2.0, light, leaf nodes for offline sites). Alternatives: RabbitMQ; PostgreSQL-only queues for the pilot (simplest; recommended until the second service exists).

### ADR-012: GPS — Proposed
**Recommendation.** **Traccar** (Apache 2.0, 200+ tracker protocols) as protocol gateway, forwarding positions to a .NET telematics service; **TimescaleDB** for position history (or native partitioning if a managed PostgreSQL without Timescale is chosen).

### ADR-013: Hosting — Proposed
**Recommendation.** Ship as containers. Pilot: a single VM (Docker Compose: app + PostgreSQL + automated backups) in an Iraqi data centre or UAE cloud. Production at scale: Kubernetes + CloudNativePG + Argo CD ([05](05-infrastructure-and-deployment.md)). Each installation chooses its own provider and region ([15](15-production-readiness.md)).

### ADR-014: Mobile — Proposed
**Recommendation.** Two .NET MAUI Blazor Hybrid apps (Driver, Warehouse) that reuse the web app's Blueprint-styled components, contracts and API clients, with native code for camera, Bluetooth printers, DataWedge and background location ([09](09-client-applications.md) §5).

### ADR-015: ASYCUDA by levels — Proposed
**Recommendation.** L0 data capture (Phase 1) → L1 SAD/manifest XML export (Phase 3) → L2 round-trip import → L3 B2G web services only through an official GCA channel. No screen-scraping ([07](07-customs-asycuda.md)).

### ADR-016: Blueprint 6 with own Blazor components — Accepted (18 Oct 2026)
**Context.** No DevExpress licence. The UI still has to be dense, professional and work in Arabic (RTL).
**Decision.** Use **Blueprint 6** (Palantir, Apache-2.0): its CSS and icon font only, vendored at pinned versions by `scripts/vendor-ui-assets.sh` (no CDN). Logistico's own Blazor components in `Logistico.Web.Client/Ui` render Blueprint markup. Base text 15 px and 36 px controls (larger than Blueprint's defaults).
**Alternatives.** Carbon (IBM; React/Web Components, lighter density); MudBlazor/Radzen (free Blazor suites, Material look); Fluent UI Blazor.
**Consequences.** No licence and no JavaScript UI framework. We maintain a small component kit ourselves. Advanced widgets (pivot, docking, ribbon) are built only if users need them. Design rules in [08](08-ui-ux-design-system.md). Extended on 19 Oct 2026 by ADR-021 (font and RTL build).

### ADR-017: Arabic by default; one culture setup — Accepted (18 Oct 2026)
**Decision.** `ar-IQ` is the default culture and `en-US` the second. Texts live in resx files per module (`ShipmentTexts`, `MerchantTexts`, `CommonText`, `ServerText`, client `UiText`). `AppCultures.Create` builds the culture for both browser and server: Western digits, `.` decimal and `,` thousands separators, a left-to-right minus sign, Gregorian calendar with Iraqi month names. The culture comes from the query string or the culture cookie; the API also honours `Accept-Language`.
**Consequences.** Amounts and dates read the same in both languages and in CSV exports. Tests fail if a text key is missing in one language or a page uses a key that does not exist. Texts with a count use CLDR plural forms (`L.Count`, keys with `_One`/`_Two`/`_Few`/`_Many`), so Arabic reads `طرد واحد`, `طردان`, `3 طرود`, `11 طردًا`.

### ADR-018: Seller orders — Accepted (18 Oct 2026)
**Decision.** Instagram and online-shop sellers are a **Merchants** module. Orders start with **pickup from the seller** (fulfilment from our stock comes next). Only staff sign in for now; customers follow a **public tracking link** that shows no personal data. A seller portal comes later.
**Consequences.** Shipments reach seller data only through `IMerchantDirectory`. COD is collected per order and settled to sellers in batches.

### ADR-019: Regional hubs and misroute alerts — Accepted (implementation detail)
**Decision.** Five hubs (Baghdad, Basra, Erbil, Najaf, Mosul) cover the governorates (`IraqHubs`). A receive, unload or route-check scan is a misroute when it happens at a hub that is **not the parcel's origin, destination or current target hub**, so the first scan at the sending hub and scans on the way back never raise a false alert.
**Consequences.** Misroutes raise an alert and are cleared by the automation sweep once the parcel reaches the right hub. The original in-memory radar was replaced by the scan log (ADR-023).

### ADR-020: One database per integration-test class — Accepted (implementation detail)
**Decision.** Each test class creates its own PostgreSQL database (`logistico_test_<id>`), migrates it on start and drops it afterwards.
**Consequences.** Test classes run in parallel without migration races or shared data. Set `LOGISTICO_TEST_DB` to use another server.

### ADR-021: Almarai font; Blueprint RTL build generated by RTLCSS — Accepted (19 Oct 2026)
**Context.** The first font (IBM Plex Sans Arabic) was not liked, and Blueprint's stylesheet is written for left-to-right: carets, input icons, menus and margins sat on the wrong side in Arabic, and hand-written overrides kept missing cases.
**Decision.** Use **Almarai** (SIL OFL, weights 300/400/700/800, vendored from `@fontsource/almarai` 5.3.0; Cairo was used first) for Arabic and Latin text. At vendor time, `scripts/vendor-ui-assets.sh` runs **RTLCSS 4.3.0** over Blueprint core and select to produce `blueprint.rtl.css` and `blueprint-select.rtl.css`; `App.razor` loads the RTL files for Arabic and the originals for English. Our own CSS uses logical properties only (enforced by a test).
**Alternatives.** Keep IBM Plex Sans Arabic or use Noto Kufi/Tajawal; override Blueprint rule by rule in `app.css`; flip with `transform` hacks.
**Consequences.** One font family for both languages, consistent line heights. Blueprint upgrades regenerate the RTL build automatically; RTLCSS runs only on the developer's machine (Node via `npx`), never in production.

### ADR-022: Built-in SVG map of Iraq — Accepted (19 Oct 2026)
**Context.** Operations need to see where parcels are across the 18 governorates and between the five hubs. A tile map (MapLibre, Leaflet) needs a tile server or a paid provider and an internet connection.
**Decision.** Draw the map in the app: `scripts/generate-iraq-map.py` converts geoBoundaries **IRQ ADM1** (CC0) into simplified SVG paths (`Ui/Map/IraqMapShapes.g.cs`). `IraqMap` shades governorates by a chosen measure and draws hubs and truck lanes.
**Alternatives.** MapLibre with self-hosted tiles (kept for live vehicle maps in Phase 2), Google Maps (cost, data leaves the company), a static image.
**Consequences.** No API key, no external requests, works offline and in both directions; about 17 KB of path data. Street-level maps for drivers remain a Phase 2 decision (ADR-012).

### ADR-023: Hub network with line-haul trucks and a persistent scan log — Accepted (implementation detail, 19 Oct 2026)
**Decision.** Each parcel records origin, destination, current and target hub. Moves between hubs happen only on a **truck** (`HubTransfer`, numbered `TR-YYYY-NNNNNN` from a PostgreSQL sequence) with a manifest: planned → loaded → received, or missing when the truck is closed without it. Every scan, including refused ones, is stored in `hub_scans`.
**Consequences.** "Where is it now?" always has an answer (a hub or a truck). The hub radar, hub station numbers and audit questions read from the scan log, so it works with several servers. Returns reuse the same trucks in the opposite direction ([02](02-domain-model.md) §10).

### ADR-024: In-process automation engine — Accepted (implementation detail, 19 Oct 2026)
**Decision.** Business automation (returns after the last attempt, next-day rescheduling, truck planning, applying simple customer requests, customer messages, SLA alerts) runs **inside the modular monolith**: immediate rules run in the same transaction as the scan or request; a sweep (`AutomationWorker`, every 60 s, configurable with `Automation:IntervalSeconds`) raises and resolves alerts. A PostgreSQL advisory lock per company makes sure only one server sweeps a company at a time. Each company edits its own `AutomationPolicy`; every automatic action is written to the automation log.
**Alternatives.** A separate worker service with a job library (Hangfire, Quartz, Wolverine); database triggers.
**Consequences.** No extra infrastructure for the pilot. When the event bus arrives (ADR-011), the sweep can react to events instead of polling. Tests set `Automation:Enabled=false` and run the sweep on demand with a controllable clock.

### ADR-025: Dark operations-console theme by default — Superseded by ADR-029 (22 Oct 2026)
**Context.** Staff work in Logistico all day, often in hubs and at night; the project wanted a Palantir-like operations-console look.
Blueprint already gives the components; the default light theme read as a generic web dashboard.
**Decision.** Dark is the default theme (light remains available and remembered per browser). All colours are `--lx-*`
tokens with a dark set in `app.css` section 14; flat panels with hairline borders, small radii, intent rails on KPIs,
upper-case micro-labels in English only. Design rules in [08 §8](08-ui-ux-design-system.md).
**Consequences.** One place to change a colour for both themes; Arabic typography untouched. Screens must be checked in
both themes (the PR template asks for it).

### ADR-026: Demand intelligence and open data — Accepted (19 Oct 2026)
**Context.** The project's goal is to improve shipping in Iraq through data: what Iraqi customers want, where and when.
**Decision.** An Intelligence area computes demand from each company's own domestic orders in PostgreSQL (governorates,
product categories recognised from Arabic/English item descriptions, ordering times, basket sizes vs refusals, trade lanes,
repeat customers) and writes plain-language findings. An authenticated CSV export publishes aggregates only, leaving out
groups under a configurable minimum (default 10 orders). Details in [16](16-data-and-insights.md).
**Alternatives.** A separate analytics database or BI tool (more moving parts before there is data volume to need it);
machine-learning classification (needs labelled data the market does not have yet; the keyword catalogue is transparent
and easy for contributors to extend).
**Consequences.** No personal data leaves the company through the export. Cross-company insight needs companies to
publish their files; an opt-in shared endpoint can follow.

### ADR-027: Open source under Apache-2.0; Docker Compose for evaluation — Accepted (21 Oct 2026)
**Context.** Logistico is meant to be an open-source system for Iraq's logistics industry.
**Decision.** Apache License 2.0 (permissive with a patent grant, the same licence as Blueprint), with
`CONTRIBUTING.md`, `SECURITY.md` (private vulnerability reporting), a code of conduct and issue/PR templates. A
`Dockerfile` and `docker-compose.yml` let anyone run the app with demo data without installing .NET; CI builds the image
on every pull request. The official production image is still produced by `dotnet publish -t:PublishContainer`.
**Alternatives.** AGPL-3.0 (forces hosted forks to share changes, but deters companies from adopting it), MIT (no patent
grant).
**Consequences.** Companies can run and extend Logistico freely, including commercially. Released as 3.0.0.

### ADR-028: Staff roles, one per person, enforced by the API — Accepted (21 Oct 2026)
**Context.** A delivery company has distinct jobs (operations, a call desk, finance, management) and the data includes
customers' phones, addresses and cash. Signed-in alone must not mean "can do everything".
**Decision.** Five roles (`StaffRoles`: Admin, Operations, CustomerSupport, Finance, Viewer), one per person, and five
policies (`StaffPolicies`: staff, operate, care, finance, administer). The host maps every module endpoint inside a
group whose convention adds `staff` for reads and `operate` for changes unless the endpoint asks for a stricter policy;
a test fails if any API endpoint has none. The browser registers the same policies to hide what a role cannot use.
Administrators manage accounts on the Team page; each team change runs in one transaction behind a per-company advisory
lock so a company always keeps an active administrator. Accounts without a role (self-registered) see no company data.
**Alternatives.** Several roles per person (more flexible, harder to explain on a hub floor); fine-grained permissions
per action (planned only if companies ask; the policies already group actions by job).
**Consequences.** New endpoints are safe by default; a new job (for example a seller portal) is a new role plus a policy.

### ADR-029: GitLab Pajamas look on Blueprint mechanics — Accepted (22 Oct 2026)
**Context.** The console look (ADR-025) suited a hub at night but read as heavy for the office, the seller portal and
people new to the system. The project wanted the clean, calm look of GitLab's Pajamas design system, while keeping
Blueprint for what Palantir built it for: dense tables, menus, popovers, dialogs and drawers, form controls, icons.
**Decision.** Pajamas sets the look and Blueprint the mechanics. Pajamas' colour, type, radius and shadow values (from
the MIT-licensed `@gitlab/ui` design tokens) are copied into `app.css` section 1 as `--gl-color-*` primitives and
`--lx-*` semantic tokens, and Blueprint's own `--bp-*` variables point at them. Blueprint's stylesheets are wrapped in a
`blueprint` cascade layer by `scripts/vendor-ui-assets.sh`; `app.css` is not layered, so its component rules (buttons,
inputs, badges, alerts, tabs, menus, dialogs, drawers, toasts, tables) always win without specificity fights. Light is
the default (GitLab's), dark is one click away. The Blazor components still emit Blueprint markup, so no page changed
for the switch. Almarai stays the typeface (Arabic first); Blueprint's icons stay. Rules in [08 §8](08-ui-ux-design-system.md).
**Alternatives.** Vendor `@gitlab/ui` (Vue components, not usable from Blazor); copy GitLab's whole 140 KB token file
(mostly unused); override Blueprint selector by selector (fragile, five-class selectors).
**Consequences.** One token file drives both themes and both design systems. A new Blueprint widget gets the Pajamas look
by adding its rule to section 3b. Re-vendoring Blueprint keeps the layer because the script adds it.

### ADR-030: Audit trail recorded by a save interceptor, in its own module — Accepted (23 Oct 2026)
**Context.** Companies need to know who changed an order, a price, a rule, a payout or an account, and when; the
security plan asks for an append-only log ([10 §5](10-security-and-compliance.md)). Writing an entry by hand in every
endpoint would miss some, and an entry saved apart from its change can disagree with it.
**Decision.** A new Audit module owns `audit.entries` ([04 §4.6](04-database-design.md)) and registers an EF Core
`ISaveChangesInterceptor`. Every module's database context (and the host's Identity context) adds the registered
interceptors, so the modules never reference the Audit module. Before a save the interceptor reads the change tracker
(record, action, each changed field before and after, a readable label such as the tracking number), opens a
transaction if none is open, and after the save inserts all entries in one statement in that same transaction. Secrets
(password hash, security stamp) are recorded as changed without their value; bookkeeping fields and records with a
history of their own (timeline, scans, logs) are skipped; JSON columns are compared by meaning. `AuditScope` names
background actors ("automation") and keeps start-up seeding out. A trigger makes the table append-only. Administrators
read it on the Audit log page and from each order.
**Alternatives.** Explicit calls in each endpoint (easy to forget); PostgreSQL triggers per table (no user or IP, schema
knowledge in SQL); an outbox to a separate store (the change and its entry could diverge until processed).
**Consequences.** Any new record type is audited without code. Bulk `ExecuteUpdate`/`ExecuteDelete` bypass the change
tracker and so the trail; none are used today, and new ones must record their own entry. Still planned: the per-tenant
hash chain, monthly partitions and a retention job (§4.6), and read access logging (sensitive reads, exports).

### ADR-031: One Flutter app, shaped by the account and controlled from the console — Accepted (28 Oct 2026)
**Context.** Senders, couriers and managers need a phone app; couriers use the company's rugged Android handhelds with
built-in scanners and Bluetooth/USB scanner guns. The earlier proposal was .NET MAUI Blazor Hybrid (two apps).
**Decision.** One **Flutter** app for Android and iOS (decided by the maintainers). The signed-in account's role decides
the screens, and the company decides from the web console which modules each role gets (`GET /api/v1/app/config`, a
**Mobile app** settings page). Foundation: **Riverpod** (state), **go_router** (role-based routes), **dio** (API),
`flutter_secure_storage` (tokens), `mobile_scanner` (camera); the hardware scanners come through a small Android plugin
(broadcast intents) and keyboard bursts. Sign-in uses **ASP.NET Core Identity bearer tokens** (`/api/v1/auth/token`,
`/api/v1/auth/refresh`); the API accepts the cookie or the bearer token on every endpoint, with the same policies.
Senders are shops created by the company; there is no public sign-up.
**Alternatives.** MAUI Blazor Hybrid (reuses web components, weaker on Android device integration and scrolling
performance); JWT (a signing key to manage, no built-in refresh-with-revocation); separate apps per role (three
releases to ship and review).
**Consequences.** Mobile code lives in `mobile/` with its own CI job. The API is the only contract: any role change or
lock on the Team page reaches the app at the next refresh. Native features beyond these (printing, background GPS) are
added as plugins when decided.
